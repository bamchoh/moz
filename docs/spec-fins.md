# FINS プロトコル実装仕様 (フェーズ 19: サーバ)

この文書は `Moz.Core/Fins/` の仕様であり、`tests/Moz.Tests/FinsServerTests.cs` (エリア表・ハンドラ・FINS/TCP 枠・ランナー) と `FinsConfigTests.cs` (設定) がこの内容をエンコードしている。両者を同時に更新すること。

moz はオムロン FINS (Factory Interface Network Service) の **CS/CJ/CP/NJ 互換のコマンド**を **FINS/TCP** (`[[server]] protocol = "fins-tcp"`) と **FINS/UDP** (`"fins-udp"`) で受ける **サーバ** (CPU ユニット側のシミュレート) である。クライアント (マスタ) は未実装。設定は docs/spec-config.md。

## メモリエリアと割り当て

オムロンのメモリはワード構成なので、すべてのエリアを **ワードテーブル** (holding / input) に写す。ビットアクセス (`CIO 100.05` 等) は写し先ワードの中のビットを読み書きする。

| エリア | ワードコード | ビットコード | 設定の `device` |
|---|---|---|---|
| CIO | B0 | 30 | `CIO` |
| W (内部補助) | B1 | 31 | `W` |
| H (保持) | B2 | 32 | `H` |
| A (特殊補助) | B3 | 33 | `A` |
| DM | 82 | 02 | `DM` |
| EM バンク 0..C | A0..AC | 20..2C | `E0`..`EC` |
| EM バンク D..18 | E0..EB | 60..6B | `ED`..`E18` |

- バンク番号は 16 進 (`E0`..`E18`)、大文字小文字は区別しない。T/C (タイマ・カウンタ現在値 89 / 完了フラグ 09)、IR/DR、カレントバンク (98 / 18)、時計は未対応 (終了コード 1101)
- **既定の割り当て**: `DM → holding 0..` (テーブル全長) だけ。他のエリアは `[[server.map]]` が必要 (割り当てが無ければ 1101)。`DM` を `[[server.map]]` に書けば既定を置き換える
- `[[server.map]]` の `kind` は `holding` か `input` (ビットテーブルには写せない)。`input` に写したエリアへの書込みは 2101
- ログ上の表記: `DM100`、`CIO100.05` (ビット)、`E0_7` (EM)

## フレーム

FINS ヘッダ 10 バイト: ICF | RSV | GCT | DNA | DA1 | DA2 | SNA | SA1 | SA2 | SID。続いて MRC/SRC (コマンド 2 バイト) とパラメータ。多バイト値はビッグエンディアン。

- 要求の ICF は bit6 = 0 (コマンド)。bit0 = 1 なら「応答不要」(処理はするが応答を送らない)。bit6 = 1 (応答) のフレームは不正として扱う (下記)
- 応答ヘッダ: ICF = 要求 ICF | 40h、RSV = 0、GCT・SID はエコー、DNA/DA1/DA2 と SNA/SA1/SA2 を入れ替え
- 応答本体: MRC/SRC のエコー | 終了コード (2) | データ。異常時はデータ無し

| コマンド | 要求パラメータ | 応答データ |
|---|---|---|
| 0101 メモリエリア読出し | エリアコード (1) \| 先頭ワード (2) \| ビット位置 (1) \| 点数 (2) | ワード: 2 バイト × 点数、ビット: 1 バイト (00/01) × 点数 |
| 0102 メモリエリア書込み | 同上 \| 書込みデータ | 無し |
| 0104 複数メモリエリア読出し | (エリアコード (1) \| 先頭ワード (2) \| ビット位置 (1)) × 項目数 | 項目ごとに エリアコードのエコー (1) + ワード 2 バイト / ビット 1 バイト |

- ワードコードではビット位置は 0 でなければならない、ビットコードではビット位置 0..15。ビットアクセスはワード境界をまたいでよい (`CIO 100.14` から 4 点 = 100.14, 100.15, 101.00, 101.01)
- ビット書込みは写し先ワードの read-modify-write (1 要求につき `IDeviceAccess.Read` 1 回 + `Write` 1 回。同じワードの他ビットを同時に書く別の経路とは競合しうる)
- 上限 (moz の値; 2000 バイト枠相当): 1 要求あたりワード 999 点、ビット 1998 点、複数読出しは 128 項目

終了コード (MRES/SRES):

| コード | 意味 | 条件 |
|---|---|---|
| 0000 | 正常 | |
| 0401 | 未定義コマンド | 0101 / 0102 / 0104 以外 |
| 1001 | コマンド長超過 | 読出しに余分なバイトがある、書込みの点数が上限超過 |
| 1002 | コマンド長不足 | パラメータが 6 バイトに満たない |
| 1003 | 点数とデータの不一致 | 書込みデータ長 ≠ 点数分、複数読出しの項目が 4 バイト単位でない |
| 1101 | エリア無し | 未知のエリアコード、または割り当てのないエリア |
| 1103 | 先頭アドレス不正 | ビット位置が規則外、先頭ワードが割り当て範囲外 (複数読出しの各項目も同じ) |
| 1104 | 終了アドレス超過 | 先頭 + 点数が割り当て範囲を超える |
| 110B | 応答長超過 | 読出し点数が上限超過、複数読出しが 128 項目超 |
| 110C | パラメータ不正 | 点数 0、複数読出しの項目 0 |
| 2101 | 書込み禁止 | `input` に写したエリアへの書込み |

検査の順序: コマンド → パラメータ長 (1002) → エリア (1101) → 割り当て (1101) → ビット位置 (1103) → 点数 0 (110C) → 点数上限 (110B / 1001) → データ長 (1003 / 1001) → 先頭 (1103) → 終了 (1104) → 書込み禁止 (2101)。

検証ベクタ (ヘッダ `80 00 02 00 0A 00 00 0B 00 01`、応答ヘッダ `C0 00 02 00 0B 00 00 0A 00 01`):

| 内容 | バイト列 |
|---|---|
| DM100 から 3 ワード読出し | `800002000A00000B0001` + `0101 82 0064 00 0003` |
| 正常応答 (1234h, 0002h, FFFFh) | `C00002000B00000A0001` + `0101 0000 1234 0002 FFFF` |
| DM100 へ 1234h, 5678h 書込み | `800002000A00000B0001` + `0102 82 0064 00 0002 1234 5678` |
| CIO 100.04 から 3 ビット読出し | `0101 30 0064 04 0003` → `0101 0000 01 01 00` (holding 値 8031h のとき) |
| 複数読出し DM100 / CIO100.04 / E0_5 | `0104 82006400 30006404 A0000500` → `0104 0000 82 1234 30 01 A0 ABCD` |
| 異常応答 (1101) | `C00002000B00000A0001` + `0101 1101` |

## FINS/TCP (`FinsTcpServer`)

枠: `"FINS"` (4) | 長さ (4; この後のバイト数) | コマンド (4) | エラーコード (4) | ペイロード。

- コマンド 0 (ノードアドレス送信): ペイロード = クライアントノード (4)。応答はコマンド 1、ペイロード = クライアントノード (4) + サーバノード (4)。クライアントが 0 を送れば自動割り当て: クライアント IP の末尾オクテット (0 / 255 / サーバノードと同じなら 1 から空き番号)。0 以外ならそのまま
- サーバノードは `[[server]] node` (1..254; 省略: bind の末尾オクテット、それが 0 / 255 なら 1)
- コマンド 2 (FINS フレーム): ペイロード = 上記のフレーム。応答もコマンド 2。ノードアドレス交換をしていない接続でも処理する (実機より寛容)。DA1 がサーバノードと違っても検査しない
- 不正 (`"FINS"` でない、長さが 8 未満または 2008 超) → MalformedFrame ログ、**無応答で接続を閉じる** (MC の不正サブヘッダと同じ)。ペイロードが FINS のコマンドフレームでない (ヘッダ + コマンドに満たない、ICF が応答) も同じ
- 未知の FINS/TCP コマンド (0 / 2 以外) → コマンド 3・エラーコード 00000003 を返して接続を閉じる
- 1 接続で要求は逐次。複数接続は同じ device を共有。接続の accept/close/error と Request ログ (`conn=c1 op=read target=DM100 qty=3 result=ok` / `err=1104`、複数読出しは `op=read-multi target=<先頭項目> qty=<項目数>`) は Modbus TCP / MC と同じイベント
- `unit_ids` は FINS には無く、無視される

## FINS/UDP (`FinsUdpServer`)

- 1 データグラム = 1 FINS フレーム (枠もノード交換も無い)。応答は送信元へ返す。ICF bit0 = 1 なら応答しない
- コマンドフレームでないデータグラムは MalformedFrame ログを出して捨てる (応答無し)
- Request ログの `conn` は送信元アドレス (`127.0.0.1:50123` 等)。ICMP 到達不能で受信が失敗しても (Windows の ConnectionReset) 止まらず ConnError ログで続行
- 標準ポートは TCP/UDP とも 9600 だが、`port` の既定は他のサーバと同じ 50200 なので明示する

テスト: エリア表 (コード ↔ バイナリ、EM バンクの 2 系統、未対応コード)、ハンドラはバイト一致ベクタ (読出し / ビット読出しのワードまたぎ / 書込み / ビット書込みの read-modify-write / 複数読出し / ヘッダの入れ替えと応答不要フラグ / 各終了コード / map の上書き)、FINS/TCP の枠 (ヘッダ検査、組み立て、ノード割り当て) とランナー (ノード交換 + 読み書き、交換なしの処理とエラー枠後のクローズ、不正マジックの無応答クローズ)、FINS/UDP ランナー (読み書き、応答不要、不正データグラムの破棄)。クライアント側は手書きのソケットコード。実機の CPU ユニットでは未検証。
