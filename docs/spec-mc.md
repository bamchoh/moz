# MC プロトコル実装仕様 (フェーズ 12: 3E クライアント / フェーズ 13: 3E サーバ)

この文書は `Moz.Core/Mc/` の仕様であり、`tests/Moz.Tests/McFrameTests.cs` (フレーム)、`McRemoteTests.cs` (クライアント結合)、`McServerTests.cs` (サーバ) がこの内容をエンコードしている。両者を同時に更新すること。

moz は三菱電機 MC プロトコル (MELSEC Communication Protocol) の Q/L/iQ-R シリーズ互換 **3E フレーム・バイナリコード** を TCP で話す。**サーバ** (CPU 側のシミュレート、`[[server]] protocol = "mc-3e"`) と **クライアント** (マスタ、`[[client]] protocol = "mc-3e"`) の両方がある (設定は docs/spec-config.md)。

## デバイス表記

`[[client.poll]]` / `[[client.push]]` の `remote` キーは GX Works と同じ表記: 英字のデバイスコード + 先頭デバイス番号。X/Y/B/W/SB/SW/DX/DY/ZR は 16 進、それ以外は 10 進。大文字小文字は区別しない。番号は 24 ビット (0..16777215) まで。

| コード | バイナリ | 種別 | 番号 | コード | バイナリ | 種別 | 番号 |
|---|---|---|---|---|---|---|---|
| SM | 91 | bit | 10 進 | SD | A9 | word | 10 進 |
| X | 9C | bit | 16 進 | Y | 9D | bit | 16 進 |
| M | 90 | bit | 10 進 | L | 92 | bit | 10 進 |
| F | 93 | bit | 10 進 | V | 94 | bit | 10 進 |
| B | A0 | bit | 16 進 | D | A8 | word | 10 進 |
| W | B4 | word | 16 進 | TS / TC / TN | C1 / C0 / C2 | bit / bit / word | 10 進 |
| SS / SC / SN | C7 / C6 / C8 | bit / bit / word | 10 進 | CS / CC / CN | C4 / C3 / C5 | bit / bit / word | 10 進 |
| SB | A1 | bit | 16 進 | SW | B5 | word | 16 進 |
| S | 98 | bit | 10 進 | DX / DY | A2 / A3 | bit | 16 進 |
| Z | CC | word | 10 進 | R | AF | word | 10 進 |
| ZR | B0 | word | 16 進 | | | | |

ビットデバイスはローカルのビットテーブル (bits / read_only_bits; 省略時 bits)、ワードデバイスはワードテーブル (words / read_only_words; 省略時 words) へ写す。`local_kind` の種別が合わなければ設定エラー。

## フレーム (3E バイナリ)

多バイト値はリトルエンディアン。

要求: `50 00` | ネットワーク番号 (1) | PC 番号 (1) | 要求先ユニット I/O 番号 (2) | 要求先ユニット局番号 (1) | 要求データ長 (2; 監視タイマ以降のバイト数) | 監視タイマ (2; 250ms 単位) | コマンド (2) | サブコマンド (2) | 先頭デバイス番号 (3) | デバイスコード (1) | デバイス点数 (2) | [書込みデータ]

応答: `D0 00` | ネットワーク番号 | PC 番号 | I/O 番号 (2) | 局番号 | 応答データ長 (2; 終了コード以降) | 終了コード (2) | [読出しデータ] (異常時はエラー情報: ネットワーク, PC, I/O, 局, コマンド, サブコマンド)

- コマンド: 一括読出し `0401`、一括書込み `1401`。サブコマンド: ワードデバイスは `0000` (ワード単位)、ビットデバイスは `0001` (ビット単位)
- 点数の上限: ワード 960、ビット 7168 (読出し・書込みとも)。先頭 + 点数は 24 ビット内
- ビット単位のデータは 1 バイトに 2 点、上位ニブルが先 (`1` = ON)。奇数点のとき最後の下位ニブルは 0 / 無視
- ルーティング: `network` (省略 0)、`pc` (省略 255 = 自局 CPU)、`module_io` (省略 0x03FF)、`module_station` (省略 0)。監視タイマは `timeout_ms / 250` (1..65535)

検証ベクタ (ネットワーク 0, PC FF, I/O 03FF, 局 0, タイマ 10h):

| 内容 | バイト列 |
|---|---|
| D100 から 3 ワード読出し | `500000FFFF03000C00100001040000640000A80300` |
| M100 から 8 ビット読出し | `500000FFFF03000C00100001040100640000900800` |
| D100 へ 1234h, 5678h 書込み | `500000FFFF03001000100001140000640000A8020034127856` |
| M100 へ 1,0,0,1,1 書込み | `500000FFFF03000F00100001140100640000900500100110` |
| 正常応答 (3 ワード: 1234h, 0002h, FFFFh) | `D00000FFFF030008 00` + `0000 3412 0200 FFFF` |
| 異常応答 (終了コード C059h) | `D00000FFFF03000B00` + `59C0 00FFFF0300 0104 0000` |

## クライアント (`McRemote`) の動き

汎用ループ `ClientPoller` (docs/consept.md、docs/spec-modbus.md のクライアント節) の `IRemoteDevice` 実装。poll 1 項目 = 一括読出し 1 要求、push 1 項目 = 一括書込み 1 要求。

- 1 本の持続 TCP 接続で要求は逐次 (3E フレームにはシリアル番号がないため同時に 1 要求)。接続は最初の周期で張り、失敗は WARN して次周期に再試行
- **終了コード ≠ 0 は「リモートの拒否」**: Request ログ 1 行 (`conn=x op=read target=D100 qty=3 err=C056`) を出し、poll ならローカルへ何も書かず、push なら再送しない (次のローカル変更で再試行)。接続は維持する
- タイムアウト (`timeout_ms`、応答ヘッダ + 本体の受信まで)、サブヘッダ不正、データ長不整合 (読出し点数に合わない、書込み応答にデータがある) は通信エラー: WARN ログ 1 行、接続を切り、次周期に再接続。push の未送達は保持される
- `plc.getVariableStatus` の `"connected"` は TCP 接続が確立していること (Modbus TCP と同じ)
- 未対応: ランダム読出し/書込み、モニタ登録、4E フレーム、ASCII コード、iQ-R 拡張デバイスコード (2 バイト)。必要になった時点で追加する

テスト: コーデックは上記ベクタでバイト一致、結合はコーデックを使わず手書きした最小 MC サーバ (ワードデバイス → words、ビットデバイス → bits、範囲外 → C056、未知コマンド → C059) を相手に poll / push / 終了コード / 無応答タイムアウトからの再接続を検証。実機の CPU では未検証。

## サーバ (`McServer` / `Mc3EServer`) — フェーズ 13

moz を MELSEC CPU に見立てる。`[[server]] protocol = "mc-3e"` で TCP (`bind` / `port`) に立ち、マスタ (SCADA、他の moz の mc-3e クライアント等) からの一括読出し / 一括書込みに device メモリで応える。

**デバイスの割り当て (`[[server.map]]`)**: MC のデバイスは 4 テーブルのメモリモデルに写す。`device = "W"`, `kind = "words"`, `offset = 1000`, `count = 100` で W0..W99 ↔ words[1000..1099]。`count` 省略時は offset からテーブルの残り全部。既定で `D → words 0..`, `M → bits 0..`, `X → read_only_bits 0..` が割り当てられており、同じコードを `[[server.map]]` に書けば置き換わる (他の既定は残る)。割り当てのないデバイスは C05B。ビットデバイスはビットテーブル、ワードデバイスはワードテーブルにしか写せない。同じテーブルの範囲が複数の map で重なってもよい (エイリアス)。

**フレーム処理** (`Mc3EServer.Handle`: 純粋。要求ヘッダ + 本体 → メモリ操作 → 応答):

- ヘッダの検査: サブヘッダ `5000` でない、またはデータ長が 4 未満 → 不正フレームとして **無応答で接続を閉じる** (Modbus の MBAP 不正と同じ扱い、MalformedFrame ログ)。これ以外の要求には必ず応答する
- 応答はルーティング 5 バイト (ネットワーク, PC, I/O, 局) をエコーし、異常時はエラー情報 (ルーティング + コマンド + サブコマンド) を付ける
- 終了コード: `C059` 未知のコマンド/サブコマンド、`C05B` 未知または未割り当てのデバイス、`C05C` 単位がデバイス種別に合わない (ビットデバイスをワード単位で等) または読み取り専用テーブル (read_only_bits/read_only_words) に写したデバイスへの書込み、`C051` 点数が 0 または上限超過 (ワード 960 / ビット 7168)、`C056` 先頭 + 点数が map の範囲外、`C061` 本体長が点数に合わない
- 書込みは `IDeviceAccess.Write` (変更通知が出る: 変数ログ・OPC UA・push が反応する)。読出し/書込みとも 1 要求 = 1 回のメモリ操作
- Request ログ 1 行: `conn=c1 op=read target=D100 qty=3 result=ok` / `err=C056`。接続の accept/close/error は Modbus TCP と同じイベント
- 未対応: ビットデバイスのワード単位アクセス (M0 を 16 点 1 ワードで読む等 → C05C)、ランダム読出し/書込み、モニタ、4E / ASCII / iQ-R 拡張。`unit_ids` は MC には無い (指定しても無視)

テスト: ハンドラはバイト一致ベクタ (読出し/書込み/各終了コード/ルーティングのエコー/map の上書き)、ランナーは moz 自身の mc-3e クライアントを相手に poll / push、不正サブヘッダで無応答クローズ。
